# ATLAS Version 1.0 — Exit Review

**Date:** 28 July 2026
**Prepared by:** Head of Product Engineering
**Question:** is ATLAS ready to be declared Version 1.0?

---

## Verdict

# NOT YET — and there is now evidence, not just an argument

Previous assessments argued that unexecuted code is unproven. That was
reasoning. This assessment has data.

**The calibration harness is the only thing in this project that has ever
been executed.** It ran six scenarios in ninety seconds and found **four
divergences, two of which were genuine bugs**:

| Bug | Symptom | Severity |
|---|---|---|
| RCI excluded unsupplied roles from the gap list | Reported *"Weak coverage (36). All roles covered and healthy."* — a score contradicting its own explanation | High. Would have told an executive coverage was fine while scoring it weak |
| Scenario engine ignored the value floor for `pursue` | Recommended "Pursue immediately" on a £1.2m opportunity against a £2m minimum | High. Would have committed a bid team to work the profile explicitly excludes |

Both would have produced confident, well-formatted, wrong advice. Neither
would have thrown an error. Neither was found by three rounds of static
review.

**Extrapolate honestly:** one executed tool, six scenarios, two real bugs.
There are 250 tests, 64 modules and 23 components that have never run.
The reasonable inference is not "it will probably be fine".

## Maturity assessment

### Engineering maturity — **6/10**

**Strong:**
- Layered architecture with a single enforced write path
- Three static gates (imports, unbound names, API contract), each written
  after the corresponding bug shipped
- 250 tests covering every model and the full lifecycle
- Seven migrations, zero model/migration drift, complete downgrade paths
- Zero secrets in repo, zero browser-exposed credentials
- Zero deprecated APIs

**Weak:**
- **Nothing executed.** Dominant finding.
- No frontend lockfile — dependencies non-deterministic
- ~43 of 64 endpoints without explicit error handling
- No CI. Every gate is run manually or not at all.

### Product maturity — **7/10**

**Strong:**
- Genuine product identity, consistently defended across 12 sprints
- Decision-first information hierarchy, enforced structurally
- Executive Focus deliberately distinct from opportunity quality
- Evidence discipline maintained throughout — inference labelled, estimates
  never presented as facts, risk suppressed rather than shown low
- Nine features explicitly cut against the traceability matrix

**Weak:**
- No user has ever seen a screen
- "Two-minute comprehension" is a design intent, never measured
- Frontend never compiled

### Intelligence maturity — **5/10**

**Strong:**
- Seven models, all weights sum to 1.0, all explainable
- Every model exposes contributions, weakest factors, improvement levers
- DCS gates the others and refuses to advise below a floor
- Full governance specification, 22/22 documented values verified against code
- Calibration harness exists and works

**Weak:**
- **Uncalibrated.** Weights are reasoned, not fitted.
- Learning loop structurally inert — needs 10+ scored outcomes, has zero
- Two known divergences from expert judgement remain open (see below)
- Model interactions unmodelled; correlated errors compound silently

### Operational maturity — **5/10** (was 3/10)

**Closed at V1.0 finalisation:**
- CI workflow (`.github/workflows/validate.yml`) enforcing all three static
  gates, the test suite, both migration directions, calibration, dependency
  audit and secret scanning. Previously every gate was optional in practice.
- Operations Guide: configuration, deployment, monitoring signals with
  thresholds, backup, recovery, incident response, performance
- Backup procedure documented with an explicit statement of what loss costs

**Still open:**
- Restore procedure **written but never rehearsed**
- No alerting — failures are found by looking
- No log aggregation
- Postgres downgrade untested
- RPO/RTO undefined (with daily backups, RPO ≤ 24h)
- Single instance only — sessions in-process

The remaining items are honest gaps, not omissions of documentation. A
restore procedure that has never been executed is a hypothesis about a
restore procedure.

## Open calibration divergences

Two remain from the harness run. Both are **judgement calls for the domain
expert**, not defects:

### 1. EFS scores the strongest opportunity 44 ("This month")

A qualified, well-evidenced, top-of-desk pursuit with 60 days to deadline.
The model reasons that a well-covered opportunity has less *to do* — which
is EFS's design taken to its logical conclusion.

**The question:** should Executive Focus mean *"where work remains"* or
*"what deserves your eyes"*? Currently it means the former, strictly. That
is defensible but produces the counter-intuitive result that your best
opportunity can rank mid-table.

**Recommendation:** add a floor so that a high-value, high-probability,
imminent opportunity cannot drop below "This week" regardless of how little
work remains. Requires your decision on the principle.

### 2. DCS advises at 31 on a single Tier 3 source

The advisory floor is 30. A lone news article with four open assumptions
scored 31 and was permitted to advise.

**Recommendation:** raise the floor to 40. One point of margin on the
platform's most important safety gate is too fine.

## Version 1.0 success criteria — measurable

Currently ATLAS can demonstrate *functionality*. These are the measures
that would demonstrate *value*. All are computable from data the platform
already stores.

| # | Metric | Baseline | V1.0 target | Source |
|---|---|---|---|---|
| 1 | **Time to understand position** | ~20 min (manual review) | **< 2 min** | Observed, pilot |
| 2 | **Briefing generation time** | — | **< 1.5s** | `generation_ms`, already instrumented |
| 3 | **Decisions with recorded reasoning** | 0% | **> 90%** | `decision_journal_entries` / decisions taken |
| 4 | **Decision turnaround** | Unknown | **< 48h** median | `turnaround_hours` |
| 5 | **Critical-role coverage** | Unknown | **> 70%** on qualified pursuits | RCI |
| 6 | **Opportunities lost to inactivity** | Unknown | **0 unflagged** | `went_stale` events |
| 7 | **Recommendation acceptance** | — | **> 60%** | Journal `response` |
| 8 | **Recommendation accuracy** | — | measurable at 10+ outcomes | `recommendation_accuracy` |
| 9 | **Qualification completion** | Unknown | **> 80%** of confirmed | Qualification states |
| 10 | **Daily open rate** | — | **10 of 10 working days** | The real test |

**Metric 10 is the one that matters.** The others can all be satisfied by
a platform nobody uses.

## Pilot readiness checklist

**Blocking — pilot cannot start**

- [ ] `bash tools/validate_release.sh` passes end to end
- [ ] `npm install` run; `package-lock.json` committed
- [ ] `alembic upgrade head` applied to a clean Postgres database
- [ ] `alembic upgrade head` applied to a v2.8 copy; migration report reviewed
- [ ] Application starts and serves the briefing
- [ ] Commercial Profile completed to ≥ 60% (below this, recommendations
      are generic and the pilot tests the wrong thing)

**Required — pilot will produce misleading results without these**

- [ ] Database backup scheduled and a restore tested
- [ ] `LOGIN_PASSWORD` rotated and removed from Railway
- [ ] Briefing generation time measured against the 1.5s budget
- [ ] Two open calibration divergences resolved
- [ ] At least 5 stakeholders mapped on 3 opportunities

**Recommended**

- [ ] `pip-audit` and `npm audit` run
- [ ] Error handling extended beyond `relationships_v2`
- [ ] Basic uptime monitoring

**Feedback capture:** the Decision Journal is the mechanism. Every accept /
edit / defer / decline is already recorded with its reasoning. A pilot that
records 20 decisions produces the data the learning loop needs — that is
the single highest-value output of the pilot, above any feature feedback.

**Known limitations to state to pilot users**

1. Recommendations are uncalibrated — reasoned weights, not fitted
2. Learning loop inert until 10+ outcomes recorded
3. Relationship position inferred from role text where stakeholders unmapped
4. Predictive engine not built (deferred deliberately)
5. Single user only — no collaboration
6. AI scanning is manual and costs money per run

## Recommended Version 1.1 priorities

**Not features. In order:**

1. **Execute everything.** Fix what surfaces.
2. **CI on every push.** The three static gates plus the test suite. They
   have caught a real bug in six consecutive sprints; making them optional
   wastes that.
3. **Resolve the two calibration divergences.**
4. **Backup and restore, tested against Postgres.**
5. **Run the pilot.** Twenty decisions with outcomes.
6. **Recalibrate against those outcomes.** This is what turns reasoned
   weights into fitted ones and activates the learning loop.

**Only then consider new capability.** The Predictive Engine remains the
right next feature — and remains correctly deferred until there is outcome
data to calibrate it against.

---

## The honest summary

ATLAS is a well-designed executive decision platform with genuine
intellectual property in its intelligence models, a consistently defended
product identity, and engineering discipline that has caught real defects
repeatedly.

**It has also never been switched on.**

The distance to Version 1.0 is not months of development. It is one
command, the fixes it surfaces, a week of operational work, and a pilot
that generates the outcome data the models need to stop being hypotheses.

Declaring 1.0 today would mean asserting that executives can confidently
base multi-million-pound decisions on recommendations produced by code that
has never run. The calibration harness — the one thing that did run —
found two bugs that would have done exactly the opposite.

**Recommendation: hold 1.0. Run the validation. The gap is small and the
cost of skipping it is the platform's core promise.**
