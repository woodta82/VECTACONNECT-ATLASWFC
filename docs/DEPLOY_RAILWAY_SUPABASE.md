# Deploying on GitHub + Railway + Supabase

A step-by-step setup for running ATLAS with the code on GitHub, PostgreSQL on Supabase, and the API, worker and web front
end on Railway. **This combination has not been run by the build session** (no GitHub repository, Railway project or
Supabase project was available to it); the settings below follow the application's own requirements and the
providers' published documentation at the time of writing. Check each provider's current documentation as you go.

## 0. What runs where

| Part | Where | Notes |
|---|---|---|
| Source code and CI | GitHub | The `commit-locks` workflow generates the lock files the images need |
| PostgreSQL 16 | Supabase | A new project used only for ATLAS |
| `api` (FastAPI) | Railway service, private only | Runs the migrations before each deploy |
| `worker` | Railway service, private only | Discovery runs, schedules, extraction, research reading |
| `web` (Next.js) | Railway service with the public domain | Proxies `/api/*` to `api` over Railway's private network |

## 1. GitHub: generate the lock files first

Both Dockerfiles install only from hash-pinned lock files and fail without them.

From 4.1.0-wfc.11 the three lock files (`frontend/package-lock.json`, `backend/requirements.lock`,
`backend/requirements-dev.lock`) are part of the source: they were generated by this repository's own `commit-locks`
workflow on 28 Oct 2026 and carried into the release unchanged. The dependency inputs have not changed since.

1. Push the source to the repository (unzip first; GitHub does not unpack an uploaded ZIP). The repository's top level
   must show `backend/`, `frontend/`, `docs/` and `VERSION`.
2. **Actions → CI** runs on every push: lock gate, backend static checks and PostgreSQL tests, the real Next.js build,
   browser journeys against `next start`, the container stack, and the dependency audits. A failing step also publishes
   the end of its log as an annotation on the run summary.
3. If a dependency input ever changes, delete the affected lock file and run **Actions → CI → Run workflow**: the
   `commit-locks` job regenerates it and opens a pull request (allow Actions to create pull requests under
   **Settings → Actions → General**).
4. Deploy only from a commit whose CI run is green.

## 2. Supabase

1. Create a new project. Note its PostgreSQL major version: ATLAS is tested on PostgreSQL 16.
2. **Turn off the Data API** for the project, or remove `public` from the exposed schemas. ATLAS never uses it, and
   otherwise Supabase may expose ATLAS tables through its REST API. After the first migration, check the project's
   security advisor.
3. In the SQL editor, run once: `ALTER DATABASE postgres SET timezone TO 'UTC';` (ATLAS also asks for UTC on every
   connection; this covers a pooler that does not pass that through).
4. Use the **session pooler** connection string (port 5432), not the transaction pooler (6543): ATLAS uses prepared
   statements. The direct connection is IPv6-only unless the IPv4 add-on is bought.
5. The first migration requires an empty `public` schema; a new project has one.

## 3. Railway: three services from the repository

| Setting | `api` | `worker` | `web` |
|---|---|---|---|
| Root directory | repository root | repository root | `frontend` |
| Dockerfile path | `backend/Dockerfile` | `backend/Dockerfile` | `Dockerfile` |
| Start command | (image default) | `python -m app.worker_main` | (image default) |
| Pre-deploy command | `alembic upgrade head && python -m app.airports_cli load --auto --if-stale 30 --optional` | — | — |
| Health check path | `/health/ready` | — | `/` |
| Port | 8000 | — | 3000 |
| Public domain | no | no | **yes** |

Variables for `api` and `worker`:

| Variable | Value |
|---|---|
| `ENVIRONMENT` | `production` |
| `DATABASE_URL` | the Supabase session pooler string |
| `LOGIN_USERNAME` | the shared username |
| `LOGIN_BOOTSTRAP_PASSWORD` | a one-time password (remove after the first sign-in) |
| `PUBLIC_ORIGIN` | the `web` service's `https://` address |
| `TRUSTED_PROXY_HOPS` | start at `2`, then check the audit log shows the browser's address |
| `BUILD_ID` | the commit SHA |
| `ANTHROPIC_API_KEY`, `AI_MODEL`, `AI_PRICE_INPUT_PER_MTOK`, `AI_PRICE_OUTPUT_PER_MTOK` | optional; leave empty to keep AI extraction and AI people reading off |
| `SEARCH_PROVIDER`, `SEARCH_API_KEY` | optional, `api` only: `brave` and a Brave Search API key to let relationship research run web searches; leave empty and searches are listed as not run, with links |
| `SEARCH_MAX_QUERIES`, `SEARCH_RESULTS_PER_QUERY` | optional (defaults 6 and 5): searches per research run, results read per search |

Variable for `web` (used at build time): `BACKEND_INTERNAL_URL` = `http://<api service name>.railway.internal:8000`.
Rebuild `web` whenever the `api` service is renamed.

Railway private networking: projects created after 16 October 2025 resolve internal names to IPv4 and IPv6, which suits
the API's `0.0.0.0` binding. In an older project internal names are IPv6-only; use a new project, or change the API's
`--host` to `::`.

Do not set `PROXY_SIGNATURE_SECRET` here: it is only for the Netlify front end (`docs/DEPLOYMENT.md` §8).

Railway's config-as-code files (`railway.json`) are marked deprecated by Railway, so this repository does not ship
them; enter the settings above in each service.

## 4. Check it (release 4.9.0 and later)

1. `https://<web>/api/health/ready` shows the release in `VERSION`, the `schema_revision` in `backend/app/main.py`
   (`EXPECTED_SCHEMA_REVISION`), and `airport_directory.full: true`. `"full": false` means the airport step could not load the
   full directory: read its message in the `api` deploy log (pre-deploy) and Settings → Data sources → Airport directory.
2. Sign in with the shared username and the bootstrap password; change the password under **Settings**; delete
   `LOGIN_BOOTSTRAP_PASSWORD` from `api` and redeploy it.
3. **Settings → Budget**: set the monthly cap, warning level and per-run cap before any research.
4. Run `tools/deploy_check.py` (`prepare`, restart `api` and `worker`, `verify --browser`) from a machine that can reach the
   deployment — see `docs/PILOT_RUNBOOK_4.9.0.md`.

Until the search and extractor keys are set, research reads the opportunity's own documents with rules only, plus organisation websites
you record; LinkedIn remains search links only. Every area that needs WFC data shows "Not connected" until files are imported under
Settings, and none of them is needed for discovery.
